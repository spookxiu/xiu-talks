## 正文

### 01 一个真实的项目场景

去年接手一个座舱项目时，我遇到了一个典型问题：

团队里有人习惯用 Android Studio + Gradle 写应用，有人坚持用源码里的 Android.bp 编译，还有人主张把三方库预编译成 so 直接集成。

三种方案各有利弊，团队争论了两周没结论。

最后我们不得不画了一张表，把每种方案的适用场景、优缺点、维护成本都列出来，才做出了选择。

这篇文章，就是那张表的延伸。

---

### 02 方案一：Android Studio + Gradle 独立编译

这是最常见的开发方式，也是大多数 Android 开发者的舒适区。

**适用场景：**
- 应用层开发，不涉及系统 API
- 需要快速迭代、频繁调试
- 团队以应用开发背景为主

**优点：**
- 开发效率高，热重载、断点调试都很成熟
- 依赖管理方便，Maven 仓库直接拉取
- 构建速度快（增量编译）
- IDE 支持完善，代码提示、重构工具齐全

**缺点：**
- 无法调用系统隐藏 API（@hide 方法）
- 无法访问系统权限（如 SYSTEM_ALERT_WINDOW 的某些行为）
- 最终需要以预编译形式集成到系统
- 与系统版本耦合度低，但集成时需要适配

**一个细节：**
我们曾用这种方式开发 Launcher，结果到了系统调试阶段，发现调用系统服务的方式在源码编译和 Gradle 编译下表现不一致，花了三天排查。

---

### 03 方案二：源码环境 + Android.bp / Android.mk 编译

这是系统开发的标准姿势，也是 AOSP 的"原生"方式。

**适用场景：**
- 系统级应用（Settings、Launcher、SystemUI）
- 需要调用系统隐藏 API
- 需要系统权限或签名
- 与系统深度耦合的功能（如 CarService 扩展）

**优点：**
- 完整访问系统 API，包括 @hide 方法
- 可以使用系统签名，获得最高权限
- 与系统其他模块的依赖关系清晰
- 编译产物直接是系统镜像的一部分

**缺点：**
- 编译速度慢（整编一次 30 分钟起步）
- 调试麻烦，需要 push 到设备或刷机
- 依赖管理原始，三方库需要手动处理
- 对开发环境要求高（需要完整源码树）

**Android.bp vs Android.mk：**
- bp 是 Google 主推的新格式，语法更简洁，编译更快
- mk 是老格式，兼容性好，很多老项目还在用
- 新项目建议直接用 bp，老项目迁移成本较高

---

### 04 方案三：预编译集成（Prebuilt）

这种方式是把模块提前编译好，以二进制形式（apk/so）放入系统。

**适用场景：**
- 三方库或 SDK（如地图、语音、支付）
- 闭源组件（供应商提供的 so）
- 编译时间过长的模块（如 Chromium）
- 跨项目复用的通用组件

**优点：**
- 大幅缩短系统编译时间
- 保护源代码（如果涉及商业机密）
- 版本稳定，不会因为源码改动而意外变化
- 可以复用已有的 CI/CD 流程

**缺点：**
- 调试困难，出问题只能看日志，无法断点
- 版本管理复杂，需要维护预编译产物仓库
- 与系统的兼容性风险（如 API 版本不匹配）
- 无法针对具体设备优化（如 so 的架构选择）

**两种预编译方式：**
- **Prebuilt APK**：直接放入 `system/priv-app` 或 `system/app`
- **Prebuilt SO**：放入 `system/lib` 或 `system/lib64`，应用通过 JNI 调用

### 05 方案对比总表

| 维度 | Gradle 独立编译 | 源码编译 (bp/mk) | 预编译集成 |
|------|-----------------|------------------|------------|
| **开发效率** | ⭐⭐⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐ |
| **调试便利性** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐ |
| **系统 API 访问** | ❌ 受限 | ✅ 完整 | ✅ 完整（需预编译时处理好） |
| **编译速度** | 快（秒级） | 慢（分钟/小时级） | 最快（直接复制） |
| **权限/签名** | 普通应用 | 系统级 | 取决于预编译时的签名 |
| **维护成本** | 低 | 高 | 中（版本管理复杂） |
| **适用团队** | 应用开发 | 系统开发 | 集成/架构团队 |

### 06 实际项目中的选择策略

经过几个项目的摸索，我总结了一个简单的决策流程：

**第一步：看模块性质**
- 是系统核心组件？→ 源码编译
- 是独立应用？→ Gradle 开发 + 预编译集成
- 是三方 SDK？→ 预编译集成

**第二步：看团队背景**
- 系统开发背景强 → 源码编译为主
- 应用开发背景强 → Gradle 开发为主，关键模块源码编译

**第三步：看迭代频率**
- 需要每天改多次 → Gradle 独立开发
- 相对稳定，周级迭代 → 源码编译或预编译

**我们项目的最终方案：**
- Launcher、SystemUI、Settings → 源码编译（bp）
- 自研业务应用 → Gradle 开发，输出预编译 APK
- 地图、语音等三方 SDK → 预编译 SO + 接口封装层

### 07 一些踩坑记录

**坑 1：Gradle 编译的 APK 在系统里权限不足**
解决方案：需要在源码里定义一个 `privapp-permissions.xml`，给预编译 APK 授予系统权限。

**坑 2：预编译 SO 的架构不匹配**
arm64 设备上放了 armeabi-v7a 的 so，导致加载失败。现在我们的 CI 会同时编译多个架构。

**坑 3：源码编译时依赖了三方 Maven 库**
Android.bp 不支持直接拉 Maven 依赖，需要先把 aar 下载下来，解压出 jar，再作为 prebuilt 引入。我们写了个脚本自动化这个过程。

**坑 4：同一个库，Gradle 和源码编译版本不一致**
曾经出现过 Gson 版本冲突，系统里一个版本，应用里一个版本，导致序列化问题。现在强制要求统一版本管理。

### 08 写在最后

编译方式的选择，本质上是**开发效率**与**系统能力**之间的权衡。

没有绝对正确的方案，只有适合当前团队、当前阶段的方案。

重要的是把每种方案的边界想清楚，在架构文档里写明白，别让后人猜。

毕竟，座舱系统的生命周期往往是 5-10 年，今天的选择会影响很多人。
